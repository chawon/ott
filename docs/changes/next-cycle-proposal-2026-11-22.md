## 3. 다음 사이클 개선 후보 3개 및 추천 순서

신규 기능만 늘리지 않고 **① 기존 기능의 치명적 마찰·데이터 신뢰 결함 제거 → ② 여러 주 반복 기록을 만드는 회상 가치 강화 → ③ 첫 기록 직후 안심 연결·`함께` 자생 루프 완성** 순으로 배치했다.

### 1순위 (즉시 착수 추천): 멀티 기기 동기화·계정 안전성·큐레이터 종료 계약 복구

- **사용자 문제**: ottline의 가장 큰 차별점은 5대 OS 크로스플랫폼과 무로그인·로컬 우선 신뢰([competitor-landscape-2026-11.md](../research/competitor-landscape-2026-11.md))이지만, `#157` 1차 코드 감사에서 **데이터 신뢰와 다중 기기 사용을 직접 깨뜨리는 계약 결함**이 확인됐다.
  1. **Windows**: `POST /api/sync/push`가 API 스키마(`changes: { titles, logs }`)와 다른 `mutations`를 보내 서버에 기록이 올라가지 않는데도 outbox를 삭제하고 `synced`로 오표기(`OttlineApiClient.cs:274-327`). 또한 `함께` 반응 `POST` 계약 불일치(`PUT` 필수), API `200 []` 시 하드코딩 큐레이터 질문 배너 상시 노출 회귀(`MainViewModel.cs:2228-2237`).
  2. **Web/PWA**: `POST /api/sync/push` `stale` 거절 시 `pullChanges()`는 수행하지만 거절된 outbox 항목을 해소하지 않아 후속 동기화가 큐 선두에서 막힘(`apps/web/lib/sync.ts:117-121,249-270`).
  3. **iOS / iPadOS / macOS**: 서버 계정 전체 삭제 실패 시 Repository는 데이터를 보존하지만 UI가 `try?`로 예외를 삼켜 성공 토스트를 오노출(`MySpaceScreen.swift:1389-1397`, `MacMySpaceAndDialogs.swift:631-636`). 기존 예정된 `2.0.1` 큐레이터 제거·macOS `함께` 필터/정렬/반응 레이스 가드와 함께 정리 가능.
- **근거 출처·시점**: `#157` 코드 감사(`2026-11-22`, `main` `8f6b751`). 실사용 발생 건수는 `미측정`(무음 실패 구조상 기존 이벤트로 포착 불가).
- **기대 효과**: "Windows에서 기록했는데 폰에 안 뜬다", "오프라인 충돌 후 동기화가 멈춘다", "삭제 실패인데 삭제됐다고 뜬다" 같은 치명적 신뢰 이탈을 선제 차단해 **다중 기기 실제 사용**과 **반복 기록**의 토대를 복구.
- **성공 지표 (분자/분모)**:
  - 계약·회귀 지표: Windows push→타 기기 pull 성공률 `100%`(QA·테스트 계정), Web `stale` 거절 후 후속 outbox 해소율 `100%`, Apple 삭제 실패 시 오류 안내 노출 `100%`, 전 플랫폼 큐레이터 UI 노출 `0건`.
  - 운영 지표(배포 후 14일 관찰): `POST /api/sync/push` Windows 요청의 `accepted > 0` 발생 확인(기존 `0` 고정), 다중 기기(2대 이상) 실제 동기화 활동 계정 수 추이(본부 기준선 확보 후 대조).
- **영향 플랫폼 / 제외 범위**: Windows(`2.0.2.0`), Web/PWA, iOS/iPadOS/macOS(`2.0.1`). API 스키마 변경 없음(`GET /api/logs/{id}/history` 인증 경계만 별도 호환 검토). Android·확장·토스·ChatGPT 제외(Android는 `2.0.5` Play 공개 확인 유지).
- **선행 API·검증·되돌림**: 선행 API 변경 불필요(기존 운영 `c693fd8` 계약에 클라이언트를 맞춤). 각 플랫폼 모의 API·격리 DB 회귀 테스트 + 실기기 2대 교차 동기화 검증 필수. DB 스키마 변경 없어 앱 이미지/패키지 롤백 가능(단, Windows는 기존 `2.0.0.0`/`2.0.1.0` 롤백 시 push 누락 재발하므로 수정본 우선).
- **상세 변경안 초안**: [cross-platform-sync-and-contract-reliability-2026-11-22.md](cross-platform-sync-and-contract-reliability-2026-11-22.md)

### 2순위 (반복 기록·회상 루프 핵심): 포스터/표지 기반 '월간 기록 달력' + 저부담 회상 카드

- **사용자 문제**: `#159` 경쟁 리서치에서 북모리·레포브·Day One의 공통 재방문 동력은 "입력"이 아니라 **"포스터/표지로 채워지는 월간 달력"과 "과거 기록을 꺼내 보는 회상 경험"**으로 확인됐다. 현재 ottline은 타임라인이 리스트 중심이고 리포트는 숫자/주간 요약 위주여서, 기록을 남긴 사용자가 다음 주·다음 달에 앱을 다시 열어볼 시각적·감성적 보상이 부족하다.
- **근거 출처·시점**: `#159` 경쟁 리서치(`2026-11-22`), `#157` 코드 감사(전 플랫폼 달력 뷰 `0건` 확인). 반복 기록 코호트 기준값은 `미측정`(본부 회신 대기).
- **기대 효과**:
  - 죄책감 없는 시각적 누적("이번 달 내 달력에 포스터·책 표지 채우기")으로 **2~4주차 반복 기록 코호트** 개선.
  - ottline 고유 강점인 **영상+책 통합 타임라인 + TPO(장소·상황)**를 한 달 단위로 돌아보고 월간 달력 카드로 공유 가능 → 마케팅 담당의 자발적 공유·유입 실험([marketing-operations.md](../marketing-operations.md))과 시너지.
- **성공 지표 (분자/분모)**:
  - 재방문·반복 기록: 월간 달력 조회 계정 중 14일 내 추가 기록(`POST`/`PATCH`) 계정 비율 vs 비조회 대조(최소 2개 완료 주간 관찰, 관리자 제외).
  - 회상 사용: `calendar_open` 도달 actor / `qualifiedActors`, 월간 공유 카드 생성 수.
- **영향 플랫폼 / 제외 범위**: **1단계 Web/PWA 선검증**(API·DB 변경 없이 기존 로컬 `watchedAt` + `posterUrl`만으로 구현 가능) → 검증 후 Android·iOS/iPadOS·macOS·Windows 순차 반영. 확장·토스·ChatGPT 제외(명시적 미지원).
- **선행 API·검증·되돌림**: 선행 API 변경 없음(기존 `/api/logs`·로컬 DB의 `watchedAt`, `posterUrl`, `type` 활용; 필요 시 기존 analytics 허용 이벤트 목록에 `calendar_open` 추가만 검토). 기존 타임라인 리스트 탭과 토글(리스트/달력)로 제공해 기존 흐름 비파괴; 효과 미흡 시 토글 제거로 즉시 되돌림 가능.

### 3순위 (첫 기록 이후 안심 연결 + `함께` 자생 루프): 첫 기록 직후 '복구/기기 연결 안심 카드' & `SavedDiscussionLink` 전 플랫폼 일관화

- **사용자 문제**:
  1. 무로그인·로컬 우선 구조는 첫 기록 진입 장벽이 낮지만, `#159` 리서치에서 드러나듯 사용자는 **"기기 바꾸면 내 기록이 사라질까?"라는 불안**이 크며, 첫 기록 1~3건을 남긴 직후가 다른 기기 연결·복구 코드 보관의 최적 타이밍이다.
  2. 큐레이터 종료(`c693fd8`) 이후 `함께`의 자생 동력은 **기록 저장 직후 같은 작품의 공개 이야기로 이어지는 경로(`GET /api/discussions/connection`)**인데, `#157` 감사 결과 Web·Apple은 구현된 반면 **Android는 `/discussions?titleId=`(다른 사람 댓글 유무 미판별)**를 호출하고 **Windows는 아예 누락**돼 있다.
  3. macOS 스토어 설치판 검증(`313827720`)이 끝나면 Web의 확장 빠른 기록 브리지(현재 Windows 전용)를 macOS까지 확대해 **브라우저→데스크톱 빠른 기록** 다중 기기 루프를 완성할 수 있다.
- **근거 출처·시점**: `#157` 코드 감사(`2026-11-22`), `#159` 경쟁 리서치(`2026-11-22`). 다중 기기 실제 사용률 및 페어링 시도/성공률은 `미측정`(계측 공백 포함, 본부 요청 중).
- **기대 효과**: 첫 기록 직후 데이터 안심(복구 카드 저장·2번째 기기 연결)과 `함께` 자생 진입을 동시에 개선하고, 페어링/이어받기 계측 공백을 메워 다중 기기 실제 사용 지표를 측정 가능하게 전환.
- **성공 지표 (분자/분모)**:
  - 다중 기기 연결: 첫 기록 1~3건 달성 계정 중 14일 내 2번째 기기 페어링 완료(`pair_success`) 및 2대 이상 실활동 계정 비율.
  - `함께` 자생 전환: 저장 완료 후 `SavedDiscussionLink` 노출 대비 클릭→상세 열람 및 댓글/반응 전환 비율.
- **영향 플랫폼 / 제외 범위**: Android(`/discussions/connection` 전환 + 첫 기록 안심 안내), Windows(`/discussions/connection` 추가 + 안심 안내), Web/PWA(안심 안내 + Mac 검증 후 `ottline://quick` 브리지 활성화 + 페어링 계측 보강), Apple(안심 안내 정렬). 토스·ChatGPT 제외.
- **선행 API·검증·되돌림**: `/api/discussions/connection`은 이미 운영 중(API 변경 불필요). 페어링/이어받기 계측 이벤트 추가 시 API 허용 이벤트 확인 선행. UI 안내 카드는 닫기/비노출 조건(`localLogs 1..3`, `linkedDevices == 1`, 세션/영구 dismiss)으로 저부담 유지하며 반응 저조 시 노출 조건 조정/제거.

## 4. 사용자(제품 오너) 방향 판단이 필요한 중기 안건

아래 2건은 제품 정책·투자 범위 판단이 필요하므로 이번 사이클에 임의 착수하지 않고 사용자 결정을 요청한다.

1. **외부 기록 가져오기(Import) 투자 여부 (후속 사이클 검토)**
   - 배경: `2026-07` TV Time 영구 종료, `2026-08` 키노라이츠의 왓챠피디아 인수 추진, 레포브의 6개 플랫폼 가져오기 성장(`#159`). 현재 ottline은 Windows의 Netflix CSV 가져오기만 존재하며 Web·모바일은 CSV 내보내기만 제공.
   - 결정 질문: 다음 이후 사이클에서 **표준 CSV / Letterboxd / Goodreads / 왓챠피디아 가져오기**를 유입·전환 기능으로 투자할지, 아니면 현재처럼 "지금부터 쌓는 가벼운 기록장"에 집중할지?
2. **Windows 기능 정합성 투자 범위 (1순위 긴급 복구 이후)**
   - 배경: `#157` 감사에서 Windows는 1순위 계약 결함 외에도 시즌/에피소드 UI, 서버 이력, KDC API, 서버 리포트, 추천 `requestId` 복구, 큰 화면 함께 2단, 영어 하드코딩 문구, 접근성 등 공백이 다수 확인됨.
   - 결정 질문: 1순위(동기화·반응·큐레이터) 긴급 수정 후, Windows를 **Web/Apple/Android와 동등한 공통 필수 수준**까지 끌어올릴지, 아니면 핵심 기록·동기화·위젯 중심의 경량 범위로 재정의할지?
