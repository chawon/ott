# 제품 기획과 지속 개선 운영

2026-11-22 사용자 요청으로 제품 기획 담당을 둔다. 기획 담당은 사용자 문제와 개선 방향, 공통 기능의 의미와 플랫폼별 지원 범위를 관리한다. 본부는 우선순위·담당·의존성·출시 순서와 완료 근거를 관리한다.

## 담당과 산출물

| 담당 | 맡는 일 | 남기는 결과 |
| --- | --- | --- |
| 제품 기획 담당 | 피드백·이용 근거 분석, 문제 정의, 대안·효과·범위 제안, 플랫폼 차이 검토 | 변경안, 기능 기준표, 허용할 차이와 남은 공백, 성공 지표·검증 시나리오 |
| 마케팅 담당 | 대상·채널·메시지·출시 안내, 유입·첫 기록·반복 이용의 관찰과 실험 제안 | 채널별 기준선, 실제 지원 범위에 맞는 안내 초안·유입 실험안과 결과 |
| 관리 본부 | 우선순위·담당 배분, 공통 결정과 API 의존성 조율, PR/CI·출시 근거 검토 | 플랫폼별 실행 카드, 출시 순서, 결정·완료 기록 |
| 플랫폼·API 담당 | 기술 설계, 구현, 호환성 확인, 테스트·PR·릴리스 | 소스·계약 변경, 검증 SHA·CI, 설치·운영 결과 |
| 운영 담당 | 인프라·백업·통계 점검과 데이터 정의 확인 | 운영·사용 근거, 집계 구간·분모·제외 조건과 한계 |
| 사용자 | 새로운 제품 방향과 주요 정책의 판단 | 결정 또는 추가 제약 |

합의된 범위의 수정과 검증은 기존 권한 안에서 이어가고, 제품 방향·주요 정책의 새 결정이 필요한 부분은 사용자 판단을 연결한다. 실제 기획 착수와 구현 착수는 각 카드에서 구분한다.

마케팅의 세부 범위는 [마케팅 운영](marketing-operations.md)을 따른다. 마케팅의 유입 근거와 기획의 사용자 문제를 연결하고, 제품·화면·계측 변경은 본부가 각 플랫폼/API 실행 카드로 배분한다.

현재 동작과 목표 동작을 각각 기록한다. 소스에 존재하는 동작, 합의된 제품 정책, 실제 출시판에서 확인한 동작을 섞지 않는다. 같은 계약 전문을 문서마다 복제하지 않고 원문으로 연결한다.

## 개선 한 건의 흐름

1. **근거 수집** — 문의·사용자 피드백·사용 통계·플랫폼 차이에서 문제를 찾는다. 대상 사용자, 발생 맥락, 근거 시점과 미확인 사항을 적는다.
2. **기획** — 현재/목표 동작, 대안과 추천 이유, 성공 지표, 공통 계약, 플랫폼별 반영·제외 범위를 정한다. 작은 수정은 같은 항목을 기존 이슈/PR에 적어도 된다.
3. **본부 조율** — 기존 카드와 중복을 정리하고 우선순위·담당·선행 작업을 정한다. API 의존 변경의 출시 순서를 연결한다.
4. **구현·검증** — 각 담당이 전용 브랜치의 PR, 테스트·CI와 설치 후보 결과를 카드에 남긴다. 다른 플랫폼에 새 누락이 생기면 차이 대장에 연결한다.
5. **출시 후 확인** — 실제 공개 버전과 사용자 결과, 지표의 변화를 확인한다. 다음 검토에서 유지·추가 개선·되돌림을 판단한다.

기획 카드의 완료는 변경안을 검토하고 실행 가능하게 만든 상태다. 기능의 전체 완료는 본부의 상위 카드에서 대상 플랫폼의 출시·검증 또는 합의된 제외 사유까지 확인해 판단한다.

## 지속 개선 검토

기존 주간 사용 통계·운영 점검 결과를 받은 뒤 다음 개선 후보를 검토한다. 기획 담당은 후보의 근거와 추천 순서를 제안하고, 본부가 현재 진행 업무·위험·의존성과 함께 다음 착수 범위를 정한다. 출시나 정책 변경으로 지원 범위가 달라지면 기능 기준표도 갱신한다.

주요 관찰 대상은 첫 기록 완료, 여러 주의 반복 기록, 연결된 여러 기기의 실제 사용, 기록·동기화 과정의 실패와 재시도다. 지표마다 기간·분자·분모·계정/클라이언트/세션 구분과 운영자·테스트 제외 기준을 남긴다. 연결 기기 수를 실제 사람이나 물리적 기기 수로 바로 해석하지 않는다. 측정하지 않은 값은 미측정으로 표시하고 측정 방법을 제안한다.

## 이슈 원문과 프로젝트판

- 새 기획 업무는 저장소 GitHub Issue를 원문으로 등록한다. 본문에 사용자 문제·근거·영향 플랫폼·산출물·완료 조건·관련 변경안과 실행 이슈를 담는다. Project V2 권한을 확보하는 절차를 착수 선행 조건으로 두지 않는다.
- 이슈에는 `role:product-planning` 라벨과 본문의 `담당 역할: 제품 기획 담당`, `플랫폼: 공통`을 사용한다. 같은 GitHub 계정을 쓰더라도 역할을 구분할 수 있게 하며 계정 assignee로 역할을 대신하지 않는다. [기획 이슈 목록](https://github.com/chawon/ott/issues?q=is%3Aissue%20is%3Aopen%20label%3A%22role%3Aproduct-planning%22)에서 업무를 찾는다.
- 기획 담당은 착수·중간 결과·자료 요청·막힌 점을 이슈 댓글에 기록하고 산출물 문서/PR을 연결한다. 본부가 Project의 `플랫폼=공통`, `담당 역할=제품 기획 담당`, 우선순위와 상태를 갱신한다. `플랫폼`은 Web·Android·iOS 등 서비스 대상을 뜻한다.
- 저장소 파일 수정이나 PR 생성이 어려우면 기능 기준표·차이 대장·개선안 초안을 Markdown으로 이슈 본문/댓글에 제출한다. 본부가 검토 후 저장소 문서와 연결된 실행 업무에 반영한다.
- 프로젝트 상태는 기존 `대기 → 진행 → 검증 → 완료`를 사용한다. 이슈 등록만으로 착수 처리하지 않고, 기획 산출물 검토와 플랫폼 기능의 출시 완료를 구분한다.
- 기존 Draft 업무는 본부가 중복 이슈를 확인한 뒤 저장소 이슈로 전환한다. 카드 상태·담당·우선순위를 보존하고 두 개의 독립된 업무로 관리하지 않는다.
- 공개 저장소 이슈에는 비공개 운영 통계·개인별 활동·접속 정보를 복제하지 않는다. 접근할 수 없는 근거는 필요한 기간·정의·범위와 함께 본부에 요청하고, 자료가 없으면 미측정/미확인으로 표시한다.
- 공통 조율은 관리 본부가, 앱 구현은 각 플랫폼 담당이 맡는다. 여러 역할이 필요하면 연결된 카드로 분리한다.

첫 업무는 [#157 핵심 흐름·기능 차이 1차 감사](https://github.com/chawon/ott/issues/157)와 [#158 다음 개선 사이클 제안](https://github.com/chawon/ott/issues/158)이다. 기존 두 Draft 카드를 이슈로 전환해 대기 상태·담당·우선순위를 유지했다. 최신 진행은 이슈 기록과 본부 프로젝트판에서 확인하며 첫 감사에서 플랫폼별 실제 근거를 보충한다. 이용 근거 수집은 병행하되 최종 개선 순서는 감사 결과·본부 제공 근거를 대조해 제안한다.
