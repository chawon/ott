# 과거 기록 복구의 기존 기기 증분 전달

상태: #171 수정 PR 준비 · 기준 main `2141230` · 브랜치 `fix/api-sync-delivery-171` · 운영 미반영.

[실행 이슈 #171](https://github.com/chawon/ott/issues/171), [기존 진단](https://github.com/chawon/ott/issues/171#issuecomment-7160228976), [공통 계약](../product-contracts.md#sync)을 따른다. #182의 목록 삭제행 제외와 달력 제품 구현은 포함하지 않는다.

## 문제와 결과

기존 API는 사용자 편집 시각 `updatedAt`·`deletedAt`을 그대로 저장하면서 그 시각이 `since`보다 큰지만 확인했다. B가 이미 최신 체크포인트를 가진 뒤 A가 과거 기록을 복구하면 서버에 저장돼도 B의 일반 pull에서 누락됐다. 수신시각이나 원시 sequence를 추가해도 미커밋 트랜잭션이 커서보다 늦게 커밋되는 누락은 남는다.

요청 `GET /api/sync/pull?since=...`, 활성 계정/기기 헤더, 응답 `{serverTime, changes:{logs,titles}}`와 각 DTO는 유지한다. 전달 순서는 별도 관리하며 사용자 논리 편집·삭제 시각을 서버 현재시각으로 바꾸지 않는다. 기존 cursor를 쓰는 기기는 일반 pull만으로 복구된 생성·수정·삭제와 필요한 canonical 제목을 받는다.

## 전달 경계와 쓰기 경로

V33은 네 개의 전달 메타데이터 테이블과 titles/watch_logs의 INSERT/UPDATE/DELETE 트리거를 추가한다. 기존 행·수정 이력·논리 시각을 일괄 변경하지 않는다.

1. `sync_pending_changes`: 원본 쓰기 트랜잭션에서 append하는 식별자 목록이다. 내용/메모/TPO는 복제하지 않는다. 원본과 같이 커밋/롤백되며 sequence 번호를 커서로 사용하지 않는다.
2. `sync_delivery_clock`: pull 트랜잭션의 발행·로그/제목 조회·DTO 구성까지 전역 fence를 보유한다. HTTP 응답 전송/메타데이터 네트워크 호출은 포함하지 않는다. 첫 재대조의 행 수에 따라 보유 시간이 늘 수 있어 운영 지연 측정이 필요하다. DB 현재시각과 이전 fence+1ms 중 큰 값으로 단조 timestamp를 발급해 밀리초 ISO 문자열 클라이언트도 같은 값을 돌려보낼 수 있다.
3. `sync_deliveries`: pull에서 현재 보이는 pending 집합만 새 전달시각으로 발행한다. 그 집합만 삭제하므로 더 작은 sequence라도 늦게 커밋한 행은 다음 발행에서 새 시각을 받는다. 각 기록의 현행 상태를 반환하는 API이며 모든 중간 수정 이벤트를 보내는 이력 API는 아니다.
4. `sync_device_cursors`: 계정/기기별 마지막 신 API 발급 cursor를 저장한다. 요청이 그 값을 정확히 echo하면 `delivered_at > since`의 증분을 반환한다. 그 외에는 현재 계정의 전체 로그·기존 계약의 전체 제목을 재대조한다. 응답 유실·이전 cursor 재시도·기기 재연결·혼합 Pod의 구 API 벽시계 cursor도 재대조 대상이다.

발행·조회·기기 cursor는 한 트랜잭션이다. 실패하면 전부 롤백돼 cursor만 앞서지 않는다. 승인된 반환 cursor를 받은 뒤 변경이 없으면 다음 응답은 비어 있다. 논리 시각 OR 조건은 쓰지 않으므로 미래 단말 시각의 행이 매 pull마다 되돌아오지 않는다. 동일 이전 cursor를 재시도하면 안전을 위해 전체 재대조가 될 수 있으며 데이터/이력을 새로 만들지 않는다.

트리거는 sync push뿐 아니라 LogService·TitleService·댓글의 기록 갱신·기존 계정 병합/소유자 변경 SQL에도 적용된다. soft-delete는 기존 DTO의 삭제 표식으로 전달한다. 기존 계정 전체 삭제·병합에서 물리적으로 제거한 로그의 전달 메타데이터를 제거하고, unlink/계정 삭제는 FK로 기기 cursor를 제거한다. 물리적 계정 삭제를 사용자용 개별 삭제 API로 바꾸지 않는다.

로그를 먼저 읽고 변경된 제목 및 각 로그가 참조하는 누락 제목을 함께 읽는다. 제목의 논리 시각이 오래됐어도 새 복구 기록이 Unknown 제목에 의존하지 않는다. 원래 제목 변경·soft-delete 신호도 전달한다.

## 충돌·동률·재시도

- 같은 계정의 sync push는 DB transaction advisory lock 이후 버전을 읽어, 먼저 커밋된 더 최신 원격 편집을 뒤의 오래된 push가 덮지 않도록 한다. 다른 계정의 제목 push를 TMDB 보강 동안 대기시키는 전역 카탈로그 락은 없다. 같은 계정의 push는 해당 요청의 메타데이터 보강이 끝날 때까지 대기할 수 있다.
- DB에 저장되는 마이크로초 정밀도로 논리 timestamp를 비교한다. 같은 로그 버전의 동일 payload/삭제 재시도는 수정·전달 receipt·이력을 추가하지 않고 수락한다. 서로 다른 동률 로그 payload와 동률의 삭제/부활 충돌은 `stale`로 기존 원격 상태를 보존한다.
- 제목은 공유 canonical 메타데이터다. 같은 논리 버전의 upsert는 보존된 canonical ID를 수락하고 메타데이터를 다시 쓰지 않는다. 첫 TMDB 보강이 이름·연도·줄거리·포스터·크레딧을 바꿔도 원본 요청의 재전송을 잘못 stale 처리하거나 다시 보강하지 않는다. 제목 삭제/부활 동률은 기존 상태를 보존한다.
- 기존 ISBN/판본·provider 식별자와 같은 계정/작품의 중복 병합 경로를 유지한다. 새 로그 ID를 받은 별칭 요청도 기존 canonical 기록으로 처리한다.

## 기존 설치판과 배포 전 누락

Web, Android Kotlin, Apple Swift, Windows C#, 이전 Expo 소스 모두 응답의 `serverTime` 문자열을 다음 `since`로 저장한다. 요청 필드나 응답 파싱을 바꾸는 앱 업데이트는 필요하지 않다. 처음 신 API를 만나는 기기는 이미 진행된 cursor가 있어도 전체 재대조를 받고, 그 응답 cursor를 돌려보내는 요청부터 일반 증분으로 인정한다. 전체 응답이 전송되었다는 사실만으로 적용 완료라고 인정하지 않는다.

V33 이전에 서버에는 있지만 B가 놓친 행도 재대조로 받는다. 서버에 아직 업로드되지 않은 Windows 원본은 #161의 별도 회복 경로가 보내야 하며, 그 원래 시각을 유지한 복구를 다른 기기에 전달하는 것이 이 변경의 범위다. 서버/기기 양쪽에서 이미 지워진 원본이나 과거에 잘못 덮인 내용을 임의로 복원하는 작업은 아니다.

클라이언트의 미전송 outbox는 API가 삭제/완료 처리하지 않는다. 최신 Web/Android/Apple/Windows 소스의 기존 논리 버전·canonical ID·outbox 보호와 **구 Expo 적용 한계**를 구분한다. 구 Expo `syncNow`는 push 실패 뒤에도 pull하고 `localDb.upsertLogLocal`은 수신 행을 조건 없이 쓰므로 별도 outbox payload가 남아도 로컬 표시 행은 덮일 수 있다. 구 Expo 사용 기기가 있으면 **실패→재시도에서 화면 기록과 보관 payload가 끝내 모두 회복되는지**를 배포 인수 조건으로 확인한다. 이 PR에서 해당 클라이언트를 수정하거나 API wire 호환만으로 그 UI 안전성까지 새로 보장하지 않는다. 기획 문서/코드/HTTP 합성 검증은 App Store·Play·Windows 실기기 출시 확인과 구분한다.

## 비용과 적용 순서

추가 비용은 원본 변경마다 작은 pending INSERT, pull의 전역 발행 fence/메타데이터 갱신과 기기별 첫 전체 재대조다. cursor가 바뀌거나 응답을 잃은 재시도에서는 추가 전체 재대조가 가능하다. 정상적인 echo 이후 변경 없는 pull은 빈 목록이다. 전달 테이블은 현행 엔터티당 한 행, cursor는 기기당 한 행이며 pending은 발행 후 제거된다. 발행 fence는 외부 메타데이터 네트워크 호출을 하지 않는다. 실제 운영 계정 규모의 첫 응답 크기·pull 지연·pending 잔여는 배포 확인 대상이다.

1. DB 백업/복구 가능 상태와 최종 병합 SHA를 본부가 확인한다. 이 PR 자체는 배포하거나 운영 DB를 변경하지 않는다.
2. V33과 API 이미지를 적용한다. V33은 구 API가 쓰는 필드·응답을 바꾸지 않아 구 Pod와 새 Pod가 잠시 공존할 수 있다. 구 API가 발급한 벽시계 cursor로 신 API에 오면 마지막 신 API 발급 cursor와 불일치하므로 재대조한다. 구 Pod 자체의 옛 조회는 고쳐지지 않으므로 drain과 신 API 단일 이미지 확인 전에는 rollout을 완료로 판정하지 않는다.
3. 기존 계정/기기의 old cursor로 재대조 → 반환 cursor echo → 다음 빈 응답을 확인한다. A의 원래 과거 시각 생성/수정/삭제를 B가 통상 증분으로 받고, 관련 제목·최신 원격 보존·동률·재전송·지연 커밋을 확인한다. 검증에는 별도 fixture를 사용하고 기존 계정을 초기화하지 않는다.
4. API-only 변경이므로 이 PR 때문에 Web/네이티브 제품 코드를 배포하지 않는다. #161/#162/#163의 플랫폼별 복구·실기기 완료는 각 담당 근거로 판단한다.
5. 되돌리면 V33·원본 데이터는 보존하고 기존 API 이미지가 동작할 수 있다. 구 이미지의 증분 한계는 다시 생기며 pending이 쌓일 수 있으므로 복구 수정본 재적용 전 완치로 보고하지 않는다. 전달 테이블을 임의로 지우거나 DB를 down-migration하지 않는다.

## 검증 근거

`SyncDeliveryDatabaseTest`는 실제 Flyway·JPA·서비스 경로와 두 DB 연결/동시 트랜잭션을 사용한다. 최초 회귀는 변경 전 실제 서비스에서 2020년 기록을 B가 놓쳐 실패하는 것을 확인했다. 새 suite는 CI 필수 PostgreSQL 실행 목록에 포함한다.

대상: V32→V33 기존 cursor 회복/시각·이력 보존, 과거 생성·수정·로그/제목 tombstone, 필요한 기존 제목, 응답 유실/이전 cursor 재시도, 승인 cursor의 빈 응답, 미래 단말 시각, 동일 시각·마이크로초·멱등 이력, canonical 중복, 역순 커밋·롤백, 251개 동일 경계, REST/소유자 SQL 쓰기, metadata 보강 재시도와 계정 간 보강 비차단. 정확한 커밋·테스트 수·CI·PR 및 본부 독립 HTTP 검증은 #171과 PR에 기록한다.
