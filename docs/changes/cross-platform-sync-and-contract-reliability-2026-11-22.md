## 사용자 문제와 완료 조건

### 현재 동작과 문제 (`main` `4db7be6` 기준)
`2026-11-22` 1차 플랫폼 감사([feature-matrix.md](../feature-matrix.md))에서 다중 기기 기록 보존과 계정 삭제 안전성을 직접 해치는 클라이언트 결함 3건이 확인됐다.

> *기준 갱신 참고*: Windows의 큐레이터 제거·함께 2단·`PUT /reactions`·내 반응 조회·추천 복구(`#142`)는 이미 [PR #156](https://github.com/chawon/ott/pull/156)(`main` `b6baa17`, [CI](https://github.com/chawon/ott/actions/runs/45000851496))로 병합·CI 완료됐으며, `2.0.1.0` 게시 후 `2.0.2.0` Store 공개·실기기 확인 대기 상태다. 이 변경안은 **아직 미해결인 동기화·삭제 안전성 결함 3건**에 집중한다.

1. **Windows 기록 업로드 무음 누락 및 기존 미반영 기록 잔존 ([#161](https://github.com/chawon/ott/issues/161))**:
   - Windows 앱이 기록 동기화 시 공통 서버 계약과 다른 형식으로 업로드 요청을 보내, 서버에 기록이 반영되지 않았는데도 대기 작업(outbox)을 지우고 동기화 완료(`synced`)로 표시한다.
   - 그 결과 Windows에서 새로 작성·수정한 기록이 다른 기기에서 보이지 않을 뿐 아니라, **이전 설치판(`2.0.0.0`·`2.0.1.0`)에서 이미 outbox가 지워지고 `synced`로 오표기된 기존 기록은 새 업로드 경로만 고쳐도 자동으로 복구되지 않는다.**
   - 부수적으로 Windows 저장 계측 이벤트명과 앱 버전 표기도 공통 기준과 어긋나 있다.
2. **Web/PWA 충돌(`stale`) 거절 시 대기 작업 미해소 ([#162](https://github.com/chawon/ott/issues/162))**:
   - 여러 기기에서 같은 기록을 수정해 서버가 충돌(`stale`)로 거절했을 때, 일반 증분 동기화(`pull`)를 실행한 뒤에도 거절된 작업이 대기열에 그대로 남아 이후 새 기록·수정까지 막을 수 있다.
   - 반대로 일반 증분 동기화가 끝났다는 사실만으로 해당 충돌 기록의 최신 서버 상태가 확보됐다고 가정해 큐를 지우면, 빈 증분 응답·계정 전환·후속 수정 상황에서 사용자 기록이 유실될 위험이 있다.
3. **Apple(iOS/iPadOS/macOS) 서버 계정 삭제 실패 시 성공 안내 오노출 ([#163](https://github.com/chawon/ott/issues/163))**:
   - 서버 계정 전체 삭제 요청이 네트워크·HTTP 오류로 실패했을 때 로컬 데이터는 보존되지만, 화면이 오류를 무시하고 기기 목록을 비운 채 삭제 성공 안내를 표시해 사용자에게 심각한 혼란을 준다.

### 변경 후 기대 동작과 필수 안전 정책

1. **Windows — 새 기록 정상 업로드 + 기존 미반영 기록의 안전한 회복 (필수 출시 조건)**
   - **신규·수정 기록**: 공통 동기화 계약에 맞춰 서버에 정상 반영하고, 서버가 실제로 수락한 기록 ID만 동기화 완료로 처리한다.
   - **기존 설치판 미반영 기록 회복 (필수)**: 업그레이드 전 이미 outbox가 삭제되고 `synced`로 오표기된 로컬 기록을 안전하게 찾아 서버로 회복해야 한다. 이때 아래 5가지 안전 원칙을 반드시 충족한다 *(구체적 조회·상태 저장 설계는 Windows·API 담당이 수행)*:
     1. **증분 pull 부재 ≠ 서버 미존재**: 증분 응답(`/sync/pull?since=...`)에 없다는 사실만으로 서버에 없는 기록으로 단정하지 않고, 계정 범위의 권위 있는 존재 확인 기준을 사용한다.
     2. **정식 식별자·판본·이력 보존**: 기존 정식 기록 ID, 작품·책 판본(ISBN) ID와 수정 이력을 훼손하거나 분리하지 않는다.
     3. **더 최신 서버 상태 보호**: 다른 기기에서 이미 더 최신 상태로 수정된 서버 기록을 Windows의 오래된 로컬 기록으로 덮어쓰지 않는다.
     4. **계정별 복구 상태 구분**: 기기 내 계정이 바뀌거나 병합돼도 다른 계정의 기록을 섞지 않는다.
     5. **반복·중단 재개 시 중복 방지**: 복구 도중 앱 종료·오프라인·재시도가 반복돼도 동일 기록이 중복 생성되지 않는다.
2. **Web/PWA — 충돌(`stale`) 기록 확인 기반의 안전한 해소 정책**
   - **충돌 정책**: 서버의 최신 버전(`SyncChange.updatedAt` 기준)을 권위 있는 상태로 반영하되, 로컬에 아직 반영되지 않은 사용자 수정 내용·수정 이력이 확인 없이 소실되지 않도록 보호 원칙을 명시한다.
   - **해소 완료 판정 조건 (필수)**: 일반 증분 pull 호출 종료만으로 해소로 판정하지 않는다. **① 현재 계정 일치, ② 해당 정식 기록 ID의 서버 최신 버전(`SyncChange.updatedAt`) 확보 확인, ③ 해소가 확인된 바로 그 outbox 작업(버전) 일치**가 모두 확인된 경우에만 해당 outbox 작업을 제거한다.
   - **보호 조건**: 빈 증분 응답, pull 실패·`401`·오프라인, 계정 전환, 충돌 해소 도중 사용자가 같은 기록에 추가 수정을 저장한 경우 **검증되지 않은 큐 삭제와 후속 수정 유실이 절대 발생하지 않아야 한다.**
3. **Apple (`2.0.1`) — 서버 계정 삭제 실패의 정직한 보존·안내**
   - 서버 `2xx` 성공을 확인한 경우에만 로컬 초기화·화면 상태 정리·성공 안내를 실행한다.
   - 네트워크·HTTP 오류 시 로컬 기록·연결 상태·화면 목록을 보존하고 KO/EN 실패 및 재시도 안내를 표시한다. *(기존 예정된 `2.0.1` 큐레이터 제거·macOS 함께 필터/정렬/경합·오류 안내 보강과 함께 출하.)*

### 필수 검증 시나리오 (인수 조건)

1. **Windows 신규·수정 교차 동기화**: Windows에서 영상·책 기록 생성 및 수정 → 동기화 → 타 기기(Web/iOS/Android)에서 동일 기록·필드·수정 반영 확인; 오프라인·5xx 시 outbox 보존 후 재연결 시 중복 없이 1회 반영.
2. **Windows 기존 설치판 업그레이드 복구 (필수)**: 기존 `2.0.0.0`/`2.0.1.0` 설치판에서 로컬에 저장·`synced` 오표기된 미반영 기록을 가진 상태로 `2.0.2.0` 업그레이드 → 누락 기록이 서버·타 기기에 정상 반영 확인 → 다른 기기에서 더 최신 수정된 기록이 덮어쓰이지 않음 확인 → 복구 중 강제 종료·오프라인 재개·반복 동기화 시 중복 생성 0건 확인.
3. **Web `stale` 충돌 안전 해소 (필수)**: 기기 A·B 동시 수정 → Web이 구버전 `SyncChange.updatedAt`으로 push해 `stale` 거절 → 아래 5가지 경계 검증:
   - 정상 해소 후 직후 신규/수정 기록 정상 push
   - 빈 증분 응답 수신 시 미검증 큐 삭제 없음
   - pull 실패·`401`·오프라인 시 큐·로컬 데이터 보존
   - 해소 중 계정 전환 시 타 계정 데이터 오염·오삭제 없음
   - 해소 중 같은 기록에 새 수정 입력 시 후속 수정 유실 없음
4. **Apple 서버 계정 삭제 실패/성공**: 오프라인·모의 `500`/`401`에서 삭제 실행 → 로컬 기록·연결 상태·화면 목록 유지 + 오류/재시도 안내(성공 토스트 0건); `200`/`204` 성공 시에만 초기화 및 성공 안내.

### 근거와 성공 지표

- **근거 출처·시점**: `2026-11-22` 1차 코드 감사([#157](https://github.com/chawon/ott/issues/157), `main` `4db7be6`). 실제 운영에서 발생한 누락·충돌 빈도는 **미측정**(코드 결함 추론을 관측된 운영 수치로 표기하지 않음).
- **QA 인수 지표 (출시 전 필수)**:
  - **Windows 동기화 반영**: 전송 대상 **로그 ID별 서버 `accepted` 확인 및 타 기기 정식 기록 반영률 `100%`** (제목만 `accepted`이고 로그는 거절된 경우·변경 없음 응답을 성공으로 오판하지 않음) + 기존 설치판 누락 기록 복구 시나리오 중복·덮어쓰기 `0건`.
  - **Web `stale` 해소**: 위 5개 경계 회귀 시나리오 통과율 `100%` (큐 블로킹·후속 수정 유실 `0건`).
  - **Apple 삭제 안전성**: 실패 시 오류 안내 및 데이터 보존 `100%`.
- **운영 관찰 지표 (출시 후 완료된 14일 KST, 관리자·테스트 제외)**:

  - **다중 기기 실제 사용 비율**: 2대 이상 활성 기기를 등록한 계정 중, 관찰 기간 내 2대 이상 기기에서 실제로 기록·동기화한 계정 비율.
    - *수집 수단·기준선 상태*: **현재 기준선 `미측정` / 기기 귀속 집계 방식 미확정**. 운영·API 담당과 데이터 출처(동기화 요청·로그·analytics 중 기기 귀속 기준), 기기 연결 정의, 추가 이벤트/집계 필요 여부를 확정한 뒤 14일 구간을 관찰한다.

## 공통 목표와 플랫폼 차이

- **관련 기능 기준표 항목**([feature-matrix.md](../feature-matrix.md)): `4. 동기화·오프라인`, `8. 삭제·초기화`, `9. 기기 표기·계측`.
- **공통 유지 결과**: 모든 전체 앱에서 로컬 우선 저장 → outbox → 서버 반영 계약 일치, 충돌 시 서버 최신 상태 확인 기반의 안전한 큐 해소, 계정 삭제 실패 시 로컬 데이터와 화면의 정직한 보존.
- **제외 및 분리 대상**:
  - **API**: 공통 동기화·삭제 계약은 이미 `c693fd8`에 운영 반영돼 있어 스키마 변경은 포함하지 않는다. 단, `GET /api/logs/{id}/history` 권한 경계는 `#155`(신규 계정 고아 기록 귀속)와 목적이 다르므로 본부가 비공개 프로젝트판에 분리한 **독립 API 검증 업무**로 추적한다(정적 소스상 확인 필요, 실제 운영 노출·피해 미확인; 격리 테스트 계정에서 본인/타 계정/미연결·해제 기기/누락 헤더 및 구형 앱 호환성 확인).
  - **Windows `#156` 기병합분**: 큐레이터 제거·함께 2단·`PUT /reactions`·추천 복구는 이미 `main` `b6baa17`·CI 완료 상태이므로 신규 구현 대상에서 제외하고 `2.0.2.0` Store 공개·실기기 검증으로만 추적한다.
  - **Android · 확장 · 토스 · ChatGPT**: 이번 변경 범위 밖(Android는 `2.0.5` Play 공개 확인 및 `#149` 별도 유지).

## 공통 계약 및 위험 고려

- **참조 계약**: [공통 API와 데이터 계약](../product-contracts.md)의 동기화(`POST /api/sync/push`·`GET /api/sync/pull`, `SyncChange.updatedAt`), 계정 삭제(`DELETE /api/auth/account`), 계측(`first_log_create`/`log_create`)을 클라이언트가 준수한다.
- **데이터 쓰기·복구 위험 (사전 검증 필수)**:
  - API 스키마 변경은 없지만, **Windows 기존 미반영 기록의 일괄 회복 쓰기와 Web `stale` outbox 제거는 실제 사용자 기록의 중복 생성·더 최신 상태 덮어쓰기·로컬 수정 유실 위험을 수반한다.**
  - 따라서 두 흐름 모두 격리된 테스트 계정과 모의 장애(빈 증분 응답·중단 재개·계정 전환·동시 수정) 회귀 테스트 통과 전에는 스토어·운영 배포를 승인하지 않는다.
- **검토한 대안**:
  - *대안 A (API가 Windows 구형 `mutations` 포맷을 추가 수용)*: 기각. 공통 동기화 계약을 이중화하며 기존에 outbox가 이미 지워진 기록을 해결하지 못함.
  - *대안 B (채택 — 클라이언트를 공통 계약으로 통일 + Windows 기존 누락 기록 안전 회복)*: 단일 공통 계약을 유지하면서 기존 사용자의 누락 기록까지 복구.

## 출시와 복구

- **적용 순서**: 공통 API 선행 배포는 불필요(`c693fd8` 계약 기준). 다만 Windows 기존 기록 회복에 계정 범위 조회 보완이 필요하다고 Windows·API 기술 검토에서 판정되면 API 확인 → Windows `2.0.2.0` 순서를 따른다. Web(`#162`)·Apple `2.0.1`(`#163`)·Windows `2.0.2.0`(`#161`)은 각 플랫폼 검증 기준을 충족하는 대로 독립 출시한다.
- **기존 데이터 보존 및 되돌림**:
  - 로컬 기록 일괄 삭제는 포함하지 않는다.
  - Web: 동기화 오류·충돌 이상 징후 시 이전 검증 이미지(`c693fd8`)로 즉시 롤백.
  - Windows: 기존 누락 기록 회복 과정에서 중복 생성·덮어쓰기 이상이 확인되면 회복 트리거를 즉시 중단하고 핫픽스 빌드 재제출(구 `2.0.0.0`/`2.0.1.0` 롤백 시 신규 push 누락이 재발하므로 수정본 우선).
  - Apple: TestFlight·실기기 검증 후 제출; 이상 시 제출 중단 및 수정 빌드 재제출.
