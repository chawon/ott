# 미래의 타임라인 — 계정별 선택과 하루 3회 정책

2026-11-08 사용자가 승인한 후속 작업이다. 기존 `feature/ottline-ux-v2-web`에서 API·DB·웹을 함께 수정한다. 기존 디자인과 로컬 우선 기록 흐름을 유지한다. Google Books 개발 키 연결·네이티브 앱·운영 배포는 이번 범위에 없다.

## 확정한 동작

- 수동 제외는 감상 기록과 별도로 계정 서버에 저장한다. 연결된 기기에서 같은 선택을 확인하고 마지막 제외를 되돌릴 수 있다. 오프라인 선택은 기기에 보관해 재연결 시 전송한다.
- 새 제외는 작품 종류와 카탈로그 ID로 구분한다. 영화·시리즈는 TMDB의 ID 영역을 구분한다. 책은 ISBN으로 판본을 확인하고, 알려진 원제·제목 별칭·저자가 일치하면 다른 판본도 같은 작품으로 다룬다. 확인할 수 없는 번역 관계를 임의 추정하지 않는다.
- 성공한 추천 생성은 **첫 생성 포함 계정당 하루 3회**다. 모든 기기·언어가 같은 횟수를 사용한다. 서버의 `Asia/Seoul` 날짜, 자정에 초기화한다. 조회·카탈로그 확인·제외·되돌리기는 횟수를 쓰지 않는다.
- 제공자 오류·잘못된 응답·불완전 응답으로 생성 전체가 실패하면 횟수를 차감하지 않는다. 선택적 보충만 실패하고 첫 유효 결과를 제공한 경우는 성공한 부분 결과 1회다. 정상적으로 생성된 빈 후보 목록은 성공한 생성으로 보관한다. 완료 기록 부족으로 제공자를 호출하지 않은 경우 차감하지 않는다.
- 새 기록은 기존 추천의 중복 제외에 즉시 반영한다. 그날의 추천 후보는 직접 저장·outbox 저장 모두 유지하며, 새 느낌·메모는 다음 추천 생성에 사용한다.
- 새 생성의 목표는 6개다. 처음에 최대 12개 후보를 요청하고 기록·수동 제외·카탈로그 중복을 거른다. 부족하면 이번 생성에서 검토한 제목·원제·별칭까지 피하도록 한 번만 추가 요청한다. 최종 조건을 다시 확인해 최대 6개를 보관하고, 보충까지 계정 추천 1회로 처리한다.
- 추천 카드에서 실제 카탈로그 작품을 확인하고 기존 기록 창의 ‘보고 싶어요·읽고 싶어요’로 이어진다. 책은 판본을 고른다. 카드나 검색 결과를 누르는 것만으로 기록하지 않는다.

## API

기존 활성 기기 인증 `X-User-Id`·`X-Device-Id`를 전 경로에서 검사한다. 응답은 `Cache-Control: no-store`다.

| 경로 | 동작 |
|---|---|
| `GET /api/recommendations/state` | 읽기 전용. 현재 언어의 후보, 최신 전체 기록·제외를 적용한 목록, 계정 제외, 횟수, 진행 상태 |
| `POST /api/recommendations/generate` | `{requestId: UUID}`. 같은 ID의 재요청은 중복 생성·중복 차감하지 않는다. 실패한 ID로 재시도 가능 |
| `GET /api/recommendations/exclusions` | 계정 제외 목록 |
| `PUT /api/recommendations/exclusions` | typed 추천 스냅샷을 멱등 저장. 안정적인 `key`와 합쳐진 메타데이터 반환 |
| `DELETE /api/recommendations/exclusions/{key}` | 본인 계정의 해당 선택만 복원. 반복 요청도 안전 |
| `GET /api/recommendations/catalog?name=&type=&year=&author=` | 실제 카탈로그 후보. 감상 기록이나 추천 횟수를 만들지 않음 |
| 기존 `GET /api/recommendations?refresh=&excluded=` | 배열 응답 호환. 새 서버 횟수와 계정 제외를 동일하게 적용 |

상태 응답:

```text
{
  items: RecommendationItem[],
  exclusions: (RecommendationItem & {key: string})[],
  quota: {date, timezone: "Asia/Seoul", limit: 3, used, remaining, resetsAt},
  generatedAt, generationId, generating, hasBatch, eligible
}
```

`hasBatch`는 같은 한국 날짜·제공자 설정의 생성 결과에만 true다. 정상 빈 결과도 true여서 자동 생성이 반복되지 않는다. 전날 결과는 다음 생성 실패 시 볼 수 있도록 목록에 남는다. `eligible`은 완료한 개인 LOG 기록이 5개 이상인지 나타낸다. COMMENT만 남긴 기록은 감상으로 간주하지 않는다.

생성 응답은 완료/재사용 `200`, 다른 기기의 생성 진행 중 `202`, 당일 3회 소진 `429`이며 모두 상태 본문을 포함한다. 제공자 오류는 `503`이다. 웹은 네트워크 결과가 불확실해도 같은 requestId를 재사용한다.

## 저장·동시성

V32는 기존 데이터를 바꾸지 않는 네 테이블을 추가한다.

- `recommendation_account_state`: 계정별 당일 성공 횟수와 2분 생성 임대
- `recommendation_batches`: 계정·언어별 마지막 성공 후보와 생성 ID
- `recommendation_generation_attempts`: 요청 ID별 진행/완료/실패, 7일간 재요청 처리
- `recommendation_exclusions`: 계정별 안정적인 키와 작품 스냅샷

임대 획득과 완료는 짧은 PostgreSQL 트랜잭션으로 처리한다. 외부 LLM·카탈로그 호출 중 DB 트랜잭션을 유지하지 않는다. 다른 프로세스의 동시 요청은 진행 상태를 반환하고 웹은 읽기 전용 상태 조회로 기다린다. 참여한 요청 ID도 저장해 연결이 끊기거나 서버가 재시작돼도 같은 언어의 완료 결과를 추가 차감 없이 재사용한다. 다른 언어의 진행에 참여한 요청은 해당 언어의 후보가 생기지 않았으면 같은 ID로 명시적 재시도할 수 있다. 늦은 완료는 현재 임대가 같은 요청일 때만 반영한다. 재시작으로 남은 임대는 2분 후 복구된다.

후보 교체와 성공 횟수 증가는 하나의 트랜잭션이다. 상태 조회도 짧은 읽기 스냅샷으로 묶어 완료 도중의 오래된 후보와 새 횟수가 섞이지 않게 한다. 저장 실패 시 이전 후보와 횟수가 유지된다. 계정 합치기는 제외를 합치고 같은 날 사용 횟수를 보존하며, 계정 삭제는 FK로 새 데이터까지 정리한다.

기존 전역/계정별 로컬 제외는 한 번만 서버 전송 대기열에 넣고 원본을 보존한다. 이후 서버에서 복원한 선택을 예전 로컬 목록으로 다시 가져오지 않는다. 계정이 바뀐 뒤 이전 계정의 대기 요청을 새 계정에 보내지 않는다.

## 카탈로그와 책

LLM이 생성한 ID·ISBN을 믿고 저장하지 않는다. OpenAI는 알려진 저자·원제·한국어/영어 제목 별칭을 반환하고, 실제 검색에서 메타데이터를 보완한다. 영상은 종류·이름·연도를 확인한다. 책은 제목과 저자까지 일치하는 결과만 자동 보완하며, 저장 전 판본 선택은 사용자가 한다.

추천용 카탈로그 조회는 영어 Google Books가 개발 환경에서 사용 불가능하면 기존 Kakao를 사용할 수 있다. 일반 작품 검색의 기존 제공자 정책은 바꾸지 않는다. 확인할 카탈로그 후보가 없으면 이름만으로 임의의 작품 기록을 만들지 않는다.

## 추천 수량 보완

처음 모델에 ‘최대 6개’만 요청하고 제외 후 보충하지 않아 목록이 줄어들던 동작을 수정했다. 최초 후보 풀은 12개, 추가 요청은 부족한 수에 여유를 둔 6~12개이며 추가 요청은 최대 한 번이다. 실제 작품의 적합성을 희생하거나 제목을 만들어 수량을 채우지 않는다. 두 번 확인해도 후보가 부족하면 확인한 수만 보여준다. 이것을 전체 카탈로그에 더 이상 작품이 없다는 판정으로 해석하지 않는다.

추가 요청이 실패해도 유효한 첫 결과가 있으면 그 부분 결과를 보관하고 1회 차감한다. 남길 결과가 하나도 없고 추가 요청도 실패하면 기존 배치와 횟수를 유지하고 503을 반환한다. 두 정상 응답이 모두 빈 경우는 기존 정상 빈 배치 정책을 유지한다. 조회·제외만으로 자동 보충 호출을 만들지 않고, 다음 명시적 새 생성에 적용한다.

운영 진단 로그 `[Recommendation]`는 생성 요청 ID별로 `requested`, `received`, `distinct`, `catalogPool`, `afterCatalog`, `afterRecords`, `afterExclusions`, `newCandidates`, 최종 `selected`/`returned`, 보충·부분 결과 여부를 남긴다. 작품명·메모·키 값은 기록하지 않는다. 모델의 최초 반환이 적은 경우와 서버 필터로 줄어든 경우를 구분할 수 있다. 브라우저에만 남은 미동기화 기록은 클라이언트에서 추가로 숨겨질 수 있다.

수량 회귀 7개는 수정 전에 모두 실패한 것을 확인했다. 최종 관련 테스트 74개(실제 PostgreSQL 12개 포함)가 통과했고, 실제 서비스와 PostgreSQL을 조합한 테스트에서 첫 요청·보충 요청이 두 번 호출되어도 완료 시도와 당일 성공 횟수는 한 번만 늘었다. 같은 요청 ID 재시도에도 추가 호출·차감이 없었다.

재시작한 개발 환경에서 별도 합성 QA 계정으로 실제 OpenAI를 호출했다. 첫 추천 6개, 2개 제외 후 기존 배치 4개, 새 추천 6개, 총 생성 횟수 2회를 확인했고 고정 ngrok에서도 같은 결과를 확인했다. 두 실제 생성 모두 모델이 12개 후보를 반환했고 6개를 선택해 보충은 필요하지 않았다. 보충 경로의 두 호출·한 번 차감은 위의 결정적 서비스/DB 회귀로 검증했다. QA 계정과 그때 만든 미참조 제목만 정리했다.

근거: `.recovery/ottline-v2/future-count-red/`, `future-count-real/result.json`. 키나 실제 사용자 기록을 검증 자료에 넣지 않았다.

## 검증 기준

- PostgreSQL 임시 스키마: 횟수 3회, 프로세스 재시작, 같은 ID 재요청, 12개 동시 기기 요청, 실패 후 같은 ID 재시도, 한국 자정, 임대 만료·늦은 완료, 원자적 저장 실패, 기기 간 제외·복원, 계정 합치기·삭제.
- 서비스/카탈로그/식별자: 전체 기록 제외·원제/ID·동명 다른 타입·책 판본/저자·캐시 유지·언어별 후보·제공자 실패·빈 결과·기록 부족.
- 웹: 서버 상태 우선, 로컬 데이터 초기화로 횟수 우회 불가, 기기 간 변경, 오프라인 대기·복원, 계정 전환 중 응답, 카탈로그 선택 전 기록 없음, 실제 기존 로컬 우선 WISHLIST 저장, KO/EN PC·모바일.
- 실제 개발 API 검증은 별도 합성 QA 계정으로 수행하고, 완료 후 그 계정·그때 만든 미참조 제목만 정리한다.

## 검증 결과

- API·카탈로그·식별자·프로필·기존 책 제공자/타임라인 회귀 **63개 통과**. 이 중 **11개는 실제 PostgreSQL의 임시 독립 스키마**에서 수행했으며 건너뛴 테스트는 없다. 12개 동시 요청·재시작·참여 요청의 재시도·언어 전환·한국 자정·임대 만료·실패 원자성·조회 스냅샷·계정 합치기/삭제를 확인했다.
- 실제 WSL 웹 프록시와 OpenAI 호출: 연결된 두 기기의 제외/복원, 첫 생성 포함 성공 3회, 한·영 공유 횟수, 동시 `200/202` 한 번 차감, 같은 ID 재요청 무료, 네 번째 `429`, 계정 합치기 후 횟수/제외 유지, 이전 기기의 `401`을 확인했다.
- 별도 실제 API 검증: 영어 선호 요청에서 기존 Kakao 책 판본 **8개**를 확인했고 조회로 감상 기록이 생기지 않았다. 실제 `/sync/push`로 남긴 WISHLIST가 기존 배치에서 즉시 제외되고 생성 ID·횟수가 유지됐다. 새 읽기 스냅샷도 실제 JpaTransactionManager에서 동작했다.
- 두 실제 API 검증은 합성 QA 계정만 사용했다. 완료 후 그 계정·그때 만든 미참조 제목·새 추천 상태까지 정리했으며 기존 사용자 데이터를 쓰거나 지우지 않았다.
- 웹 helper **8개**, TypeScript·수정 파일 Biome·Next.js 16.3.8 빌드 통과. 격리 브라우저 주요 시나리오 **11개** 통과. 카탈로그에서 실제 IndexedDB WISHLIST/outbox까지 이어지는 기존 저장 흐름을 확인했다. API는 전부 가로채 실제 서버 쓰기는 없었다.
- 모바일 도서 판본 목록의 가로 나열을 추가로 재현해 카탈로그용 시트로 분리했다. 최종 모바일 KO/EN·PC 판본 목록과 닫기 버튼 영역은 수정한 빌드에서 별도 통과했다. 판본 선택 전 기록이 없고 사용자의 WISHLIST 저장 시 선택한 ISBN/provider로 실제 IndexedDB 기록과 outbox가 생기는 것도 세 화면에서 확인했다.

비공개 검증 근거: `.recovery/ottline-v2/future-account-real/`, `future-state-red/`, `future-state-*/`. 로컬은 Flyway 비활성 상태라 V32 신규 테이블만 개발 DB에 적용했다. 운영은 V32를 포함한 API 배포가 먼저 필요하며 이번 작업에서는 배포하지 않았다.

## 개발 환경 반영

검증한 Next.js 빌드를 기존 `172.24.75.199:3000`에 반영했다. API `8080`과 고정 ngrok도 유지했다. WSL 한·영 타임라인·API health·고정 ngrok 타임라인 모두 HTTP 200, 세 개발 서비스 active를 확인했다. 서버 런타임 자격증명이 웹 정적 자산에 포함되지 않는지도 확인했다. 이전 빌드는 비공개 snapshots에 보관했다.

3000에 반영한 실제 번들에서도 서버 횟수 시나리오와 모바일 영문 판본 선택→WISHLIST 저장 회귀를 다시 통과했다. 브라우저 API는 격리했으며 실제 서버 쓰기는 0건이다.
